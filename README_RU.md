# Платформа версионирования Terraform-модулей в sre: Полное практическое руководство от А до Я

> **О чем этот документ:**  
> Это пошаговое руководство на человеческом языке, объясняющее, **зачем** нужна эта система, **как** в ней работать каждый день простому инженеру, **что** происходит под капотом и **почему** вы больше никогда не уроните прод при изменении общих модулей.

---

## 1. В чем проблема сейчас и зачем всё это нужно?

### Как устроена жизнь в репозитории сейчас (Антипаттерн):
В репозитории есть папка `terraform-modules/parts/aws/aws_eks`.  
Все наши 27 кластеров (включая production-кластер `tmna`, `stage` и тестовый `madmax`) подключены к этой папке через обычные относительные пути файловой системы:
```hcl
# terragrunt.hcl в production/tmna/cluster
terraform {
  source = "../../../../../terraform-modules//parts/aws/aws_eks"
}
```

### Чем это опасно («Эффект русской рулетки»):
1. **Любой коммит в мастер сразу летит на прод:** Если вам нужно добавить новую фичу или переменную в модуль EKS только для тестового кластера `madmax`, вы меняете код модуля и мёржите PR в `main`. В эту же секунду **все остальные 26 кластеров**, включая прод, получают этот код.
2. **Случайный снос ресурсов:** Если в модуле изменился параметр нод-группы или опечатались в имени, утренний запуск Jenkins/Atlantis на проде может удалить и пересоздать боевой кластер.
3. **Нельзя сделать Canary-выкатку:** Нельзя раскатить новую версию модуля сначала на `madmax`, посмотреть недельку, потом на `stage`, и только через месяц — на `production`. Сейчас либо все на старом, либо все на новом.

## 2. Как это работает теперь (Новая архитектура)

Каждый модуль в каталоге `terraform-modules/parts/` становится **автономным пакетом с четким номером версии** (Git-тегом):
* Например: `modules/aws-eks-v1.0.0`, `modules/aws-eks-v1.1.0`, `modules/aws-eks-v1.2.0`.

А каждый кластер в Terragrunt подключает модуль с фиксацией конкретного тега:
```hcl
# Production зафиксирован на стабильной версии v1.0.0 и не ломается!
terraform {
  source = "git::https://github.com/zededa/sre.git//terraform-modules/parts/aws/aws_eks?ref=modules/aws-eks-v1.0.0"
}
```

### Что это дает:
* Вы можете хоть 50 раз менять код модуля в `main` — **на проде ничего не изменится**, пока вы явно не измените строчку `ref=...` в файле деплоймента продакшена.
* Откат любой аварии занимает **30 секунд**: меняем `v1.2.0` обратно на `v1.1.0` и применяем.

## 3. Как обычному инженеру с этим работать (День за днем)

Вам **НЕ нужно** вручную ставить теги в Git, писать списки изменений руками или ждать ботов, пока вы разрабатываете код. Весь процесс состоит из 4 простых шагов:

```text
┌────────────────────────────────────────────────────────────────────────┐
│  ШАГ 1: Локальная разработка модуля                                    │
│  - Меняете .tf файлы в terraform-modules/parts/aws/aws_eks             │
│  - Запускаете быстрый тест: tofu test (1 секунда, 0 обращений в AWS)   │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│  ШАГ 2: Проверка на реальном dev-кластере ДО создания релиза           │
│  - Переходите в каталог dev-кластера madmax                            │
│  - Запускаете: TG_SOURCE=... terragrunt plan                           │
│  - Terragrunt берет ваш локальный код с диска, игнорируя тег Git       │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│  ШАГ 3: Коммит по стандарту Conventional Commits                       │
│  - git commit -m "feat(aws-eks): add support for karpenter node role"  │
│  - Открываете Pull Request -> CI запускает матрицу тестов              │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│  ШАГ 4: ВСЁ ОСТАЛЬНОЕ ДЕЛАЮТ БОТЫ (Автоматика)                         │
│  1. PR вливается в main.                                               │
│  2. Release Please сам выпускает тег: modules/aws-eks-v1.3.0           │
│  3. Renovate сам открывает PR на обновление dev-кластера madmax        │
│  4. Вы проверяете dev-кластер -> затем обновляете staging и prod       │
└────────────────────────────────────────────────────────────────────────┘
```

## 4. Подробное пошаговое руководство (Deep Dive)

### Сценарий: Вам нужно добавить новую фичу в модуль `aws_eks`

#### Шаг 1. Создаем ветку и меняем код
```bash
git checkout -b feat/add-karpenter
```
Открываем `terraform-modules/parts/aws/aws_eks/main.tf` и добавляем нужный ресурс или output:
```hcl
output "karpenter_node_role" {
  description = "IAM role for Karpenter nodes"
  value       = aws_iam_role.karpenter.arn
}
```

#### Шаг 2. Запускаем мгновенный юнит-тест (Без интернета и без AWS!)
В каждом модуле есть папка `tests/unit.tftest.hcl`. Там настроен `mock_provider "aws" {}`.  
Он перехватывает все вызовы к Amazon API прямо внутри OpenTofu.

Запуск:
```bash
cd terraform-modules/parts/aws/aws_eks
tofu test
```
* **Время:** 1.1 секунды.
* **Что проверилось:** Что HCL-синтаксис верный, условия `count` работают, регулярные выражения валидации переменных не ломаются. Токены AWS не нужны.

#### Шаг 3. Как посмотреть Terragrunt Plan на dev-кластере ДО релиза?
Это самый частый вопрос: *«Как мне увидеть diff на madmax, если новый тег еще не выпущен?»*

Для этого в Terragrunt существует стандартная переменная `TG_SOURCE`:
```bash
cd terragrunt/deployments/development/zedcloud-madmax/cluster
TG_SOURCE=../../../../../terraform-modules//parts/aws/aws_eks terragrunt plan
```
* **Что делает эта команда:** Terragrunt **временно игнорирует тег Git** в `source` и подтягивает ваш незакоммиченный код прямо из соседней папки на диске.
* Вы видите точный diff на dev-окружении своими глазами.

#### Шаг 4. Делаем коммит
Чтобы релизный бот понял, что вы изменили, коммит пишется по правилу Conventional Commits:

* Если добавили новую фичу:
  ```bash
  git commit -m "feat(aws-eks): add karpenter node role support"
  ```
  *(Бот автоматически увеличит минорную версию: v1.2.0 -> v1.3.0)*
* Если исправили баг:
  ```bash
  git commit -m "fix(aws-eks): fix security group egress rule"
  ```
  *(Бот автоматически увеличит патч-версию: v1.2.0 -> v1.2.1)*

*Допустимые скоупы в скобках:* `aws-eks`, `irsa-role`, `rds-postgres`, `s3-bucket`, `sandbox-test`.

#### Шаг 5. Открываем Pull Request на GitHub
При создании PR автоматически запускается **Matrix CI**:
1. Проверка форматирования (`tofu fmt -check`).
2. Проверка безопасности (`trivy config` на уязвимости и открытые порты).
3. Авто-генерация документации `README.md` через `terraform-docs`.
4. Параллельный запуск `tofu test` для каждого модуля.
5. Проверка заголовка PR (`Semantic PR Linter`).

Коллеги ставят Approve $\rightarrow$ вы мёржите PR в `main`.

## 5. Что происходит ПОСЛЕ мержа в `main` (Магия ботов)

Вы смержили свой PR. Что происходит дальше?

### 1. Release Please создает Release PR
Через 30 секунд бот Release Please анализирует коммит `feat(aws-eks): ...` и открывает PR с названием:
> `chore: release main`
Внутри этого PR он сам:
* Увеличивает версию в манифесте: `1.2.0 -> 1.3.0`.
* Добавляет красивое описание вашей фичи в `CHANGELOG.md`.

Вы (или тимлид) просто нажимаете кнопку **Merge** на этом Release PR.  
**Всё! Релиз готов:** в репозитории автоматически появляется Git-тег `modules/aws-eks-v1.3.0` и создается официальный GitHub Release.

### 2. Как обновляются кластеры (Renovate Bot и Canary Rollout)
Вам **НЕ нужно** руками ходить по всем папкам и менять строчки `ref=...`.

Renovate Bot видит новый тег и работает по правилу **Canary-выкатки**:
1. Он **НЕ трогает прод**.
2. Он открывает PR на обновление **только для dev-кластера `madmax`**:
   `chore(deps): update dependency to v1.3.0 in madmax`
3. Вы или Atlantis запускаете `plan` в этом PR, смотрите diff, мёржите и применяете на Dev.
4. Убедились, что `madmax` работает стабильно?
5. Открываете **[Dependency Dashboard](https://github.com/xandrei-zededa/sre-versioning-sandbox/issues/4)** в GitHub Issues, ставите галочку напротив `staging` или `production` $\rightarrow$ бот создает аккуратный PR для прода.

## 6. Шпаргалка основных команд

| Что нужно сделать | Команда |
| :--- | :--- |
| **Проверить модуль тестом** | `cd terraform-modules/parts/... && tofu test` |
| **Проверить форматирование** | `tofu fmt -recursive terraform-modules` |
| **Проверить безопасность** | `trivy config --severity HIGH,CRITICAL terraform-modules` |
| **Локальный сухой прогон Terragrunt** | `TG_SOURCE=<путь_к_модулю> terragrunt plan` |
| **Запустить все pre-commit проверки** | `pre-commit run --all-files` |
| **Запустить демонстрацию всего цикла** | `./scripts/demo-walkthrough.sh` |

## 7. Часто задаваемые вопросы (FAQ)

#### В: Не устану ли я от сотен PR'ов при каждом обновлении?
**О:** Нет. В нашем конфиге включена группировка кластеров и **Dependency Dashboard** (Issue #4). Боты не спамят на каждый чих. Для dev-кластеров создается один общий PR, а прод обновляется только тогда, когда вы сами поставите галочку в дашборде.

#### В: Что делать, если на проде после обновления что-то сломалось?
**О:** Откат занимает 30 секунд. В `terragrunt.hcl` продакшена меняете одну цифру:  
`ref=modules/aws-eks-v1.3.0` $\rightarrow$ `ref=modules/aws-eks-v1.2.0`  
и запускаете `terragrunt apply`. Все возвращается в точное предыдущее состояние без `git revert` в кодовой базе.

#### В: Нужно ли переводить все 65 модулей сразу?
**О:** Ни в коем случае. Переход делается поэтапно: сначала 1 пилотный модуль (`sandbox-test`), затем 1 боевой (`aws_eks`), и только потом остальные. Все старые модули могут спокойно продолжать работать на старых путях, пока до них не дойдет очередь.
